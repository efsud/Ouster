# SR-436 observed speeds in Altamonte Springs

## Capture and view

1. Double-click [scripts/record_sr436_hour.command](../scripts/record_sr436_hour.command).
   Enter the BlueCity API username and password in Terminal; both prompts hide
   input. Do not paste credentials into chat, shell commands, source, or issue
   reports. The launcher checks actual FRAME messages during a 60-second preflight,
   then saves a common one-hour receipt-time window. For a two-hour session,
   open [the two-hour launcher](../scripts/record_sr436_two_hours.command) instead.
   Each session gets its own archive; the dashboard opens the latest attempt.
   Late sensors and restarts
   leave gaps in that window. Keep Terminal open; the launcher keeps the Mac awake.
2. Double-click [scripts/open_sr436.command](../scripts/open_sr436.command), or
   run `./.venv/bin/python -m deepctm.florida_preview` from the repository and
   open [the local dashboard](http://127.0.0.1:8770/).
3. Use the per-sensor checkboxes, direction and SDK class filters. The initial
   extent is the entire recording window. Scroll over the plot to zoom at the
   pointer, use the slider to move through time, and press **Full hour** (or **Full recording** for a two-hour session), or
   double-click to reset. Export PNG saves the current plot, including its time
   range, approximate distance and color scale. Both axis and hover use
   America/New_York (with EDT/EST as appropriate).

The existing Python 3.11 SDK environment is required; see the
[BlueCity SDK documentation](../Data%20API/Realtime%20SDK/README.md) and
[wire/schema reference](../Data%20API/Realtime%20SDK/README_sub.md).
The viewer is loopback only, needs no login, and does not serve raw recordings.
Florida sessions and derived artifacts live under ignored `data/sr436/`; the
Toronto capture folders and the shared live-dashboard DB are untouched.
Worker credentials are passed through private pipes, not persisted or placed on
the command line. Archive rows preserve the SDK protobuf bytes (base64),
decoded payload and sensor timestamp fields, local receipt time, UDID, session
ID and object classes. There is no automatic deletion. Failed sensors are
reported individually; healthy streams continue. A token request or a signal
event alone is not proof of FRAME reception.

## Arm both peak windows in advance

Open [the peak recorder](../scripts/arm_sr436_peaks.command), enter the recording
date, and complete the hidden login. It validates the BlueCity API login now
and keeps the credentials only in process memory, then connects to the sensors
one minute before each fixed Eastern window (7–9 a.m. and 4–6 p.m.). Login
acceptance does not establish frame reception; each window has its own capture
manifest. Keep Terminal open and the Mac powered, lid open and connected.
Closing Terminal, signing out, or restarting stops the schedule. If the login
is rejected, the launcher offers another private attempt and does not arm.

## Geometry and interpretation

From west to east, the [FDOT signal inventory](https://services1.arcgis.com/O1JpcwDW8sjYuddV/ArcGIS/rest/services/Traffic_Signal_Locations_TDA/FeatureServer/0)
and [District Five diversion guide](https://www.cflsmartroads.com/projects/design/tsp/Regional_integrated_corridor_mgmt/Detour_Maps/I-4_Implementation_Guide-RICMS.pdf)
place the sites as follows. Distance accumulates straight segments between FDOT
signal points, including the intervening mall signal. It is neither surveyed
road length nor LiDAR placement.

| Signal station | Approx. distance from Cranes Roost | FDOT signal |
|---|---:|---|
| Cranes Roost / Northlake | 0 m | 77112 |
| Hattaway / Festival | 204 m | 77113 |
| Renaissance / Plaza Entrance | 420 m | 77114 |
| Essex | 636 m | 77115 |
| Palm Springs | 1,028 m | 77117 |
| Boston | 1,311 m | 77118 |

FDOT groups Renaissance and Plaza Entrance at one signal. Their two UDIDs are
independent observations; neither exact sensor placement nor overlapping
coverage is confirmed. SDK coordinates are sensor-relative metres, and the
object's `rotation` is its box angle, not a sensor calibration angle. In the
absence of local orientation and origin, scalar speed is still available from
adjacent XY displacements, but a local coordinate cannot be placed along the
corridor. The viewer uses a horizontal speed strip at that signal station and
marks its direction unknown. No Toronto rotations or traffic-shape fitting are
used.

When site calibration arrives, save a local JSON under `data/sr436/` keyed by UDID.
Each entry needs `origin_lat`, `origin_lon`, `origin_station_offset_m` (signed
relative to the public signal), `east_unit_xy` (unit vector in SDK XY),
`roi_m` ([min along, max along, min lateral, max lateral], relative to sensor
origin), and `source` (installation map or measurement provenance). Regenerate:

```sh
./.venv/bin/python -m deepctm.florida_tracks --calibration data/sr436/calibration.json
```

This projects measured local points onto the road tangent and classifies
direction by the sign of net displacement (at least 3 m and 70% of total
longitudinal travel). It does not validate lanes, turns, or crossing identities.
Refresh the browser after regenerating. The axis still uses the approximate FDOT
stationing.

## Breaks and evidence

The audit counts frames, first/last receipt, sensor timestamp endpoints, session
changes, frame gaps over 3 seconds (including window edges), clock steps,
missing or duplicate objects, implausible speeds, and ROI exclusions. An
observed segment requires the same site, session, object ID and SDK class in
consecutive frames, both positive relative clocks within one second, clock-rate
ratio 0.5–2, and displacement speed at most 216 km/h. The horizontal axis uses
receipt time, so network buffering remains a potential source of time shift.
Absolute sensor clock alignment has not been verified. The plot retains up to
two original adjacent pairs per second per fragment for browser performance.
It does not draw connecting lines between retained pairs. Disappearance counters
alone cannot distinguish occlusion, tracking-ID replacement, field-of-view
exit, or missed detection. Diagnose any particular case from adjacent raw frames
and the calibrated field of view. Red on the speed scale means slow movement,
not a verified red signal.

## DeepCTM decision

Reviewed Cellitti, Di Rocco and Ferraro Petrillo, *A Physics Informed GNN for
Traffic Prediction: the DeepCTM Model*, particularly §§3–5, Figures 4–5, and
Tables 1–2 (user-supplied paper). The paper combines physical CTM evolution and
learned residual memory, directional message passing, a sensor-mask gate, PEC,
and masked prediction and physical losses. It predicts aggregate cell
flow/density/speed. No individual vehicle trajectory, departure continuation,
or downstream ID match follows from those three variables. The paper leaves
some recurrence, loss and integration details unspecified and gives different
60-minute full-model RMSE values in Tables 1 and 2.

The Toronto code and [method notes](deepctm.md) include a 60-second exploratory
adaptation and virtual tracers. Florida does not invoke that code or display
tracers. One hour yields only four 15-minute bins before coverage screening,
insufficient for independent context, validation, and test periods at the
paper's cadence and forecast horizons. A shorter step creates more bins but
does not create independent days or traffic regimes. With no Florida frames
and no calibrated cells there is no basis for estimates now.

A future experiment should use directed road cells with measured geometry,
appropriate turn/boundary and signal inputs, and defensible estimates of flow,
density and speed from trajectories. Virtual cells remain masked for
supervision; missing observed samples retain explicit masks on the regular
grid. Split by chronological blocks with complete context and target windows
inside each split. Compare held-out aggregate errors against persistence and
calibrated pure CTM, and check vehicle balance using rate × duration and
density × cell length. Document cadence, CFL substeps and recurrence choices.
Only then show aggregate estimates as a separate labeled layer. Any future
track continuation would require an observed departure anchor, recorded
provenance, uncertainty, and independent evidence before claiming a downstream
identity. Missing or unmatched tracks stay visually distinct.

```sh
python3 scripts/make_sr436_test_fixture.py /tmp/sr436-fixture-new
./.venv/bin/python -m deepctm.florida_preview --base /tmp/sr436-fixture-new --port 8771
```

Chromium available (`PLAYWRIGHT_MODULE` and `CHROME_EXECUTABLE` can point to
local installations). This fixture has no field data and is never copied to
the real Florida archive.
